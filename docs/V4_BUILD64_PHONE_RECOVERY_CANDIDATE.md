# Build64 phone deep-recovery production candidate

Build64 is the first production-candidate promotion after the Build45–63 diagnostic sequence. **Build44 remains the latest qualified production baseline until the Build64 physical gate passes.**

## Evidence from Build63

The qualified Go 1.26.0 Build63 host artifact closes the primary B/mild case as `fourth-pair-continuation-recovery`:

- B/mild freezes 937 fourth-pair continuation states; 935 qualify and exactly **1 authenticates**.
- The authenticated state is candidate 10, side-pair rank 3 / seed rank 3 / fourth-pair rank 7 / continuation index 7.
- Its proposal score is `0.302815`, held-out validation is `0.240486`, and HMAC authenticates exactly.
- Its independent post-hoc oracle error is `28.868 px`. It is **not** the geometry-minimum state; the best post-hoc geometry is `22.099 px` and does not authenticate. This is important evidence that oracle geometry did not choose the successful state.
- B/angle freezes 6198 continuation states, with **0 qualified and 0 authenticated**.

The Build63 recovery is therefore generated by public proposal evidence, survives independent held-out qualification, and succeeds only at final authenticated data decode. HMAC remains a final verifier rather than a geometry search signal.

## Build64 hypothesis

Can the exact blind search family demonstrated by Build63 be added as a final production fallback without regressing the Build44 physical matrix?

Build64 makes no encoder, wire-format, pilot, strength, ECC/Hamming, whitening/HMAC-domain, proposal-score, threshold or quorum change. It adds one fallback after the existing phone path fails.

## Production-candidate ordering

`v4-extract-phone` keeps the existing ordering unchanged:

1. Build41 direct phone geometry/data path;
2. Build43 side-pair fallback;
3. Build42 qualified-bank/list data fallback;
4. Build40 residual warp fallback;
5. **Build64 deep recovery**, only if the historical path still has not authenticated.

If Build41/43 cannot form the historical two-geometry accepted ensemble, Build64 is also allowed to run immediately before returning the previous `geometry not accepted` failure. This is required for B/mild, whose Build43 bank historically contains only one held-out-qualified candidate.

Existing Build44 PASS captures must return before Build64 is attempted.

## Freeze barrier

Build64 reproduces the Build63 deep search as a production-candidate bank:

1. Build47 extended public candidate bank;
2. top4-per-side-pair seed selection;
3. 2px roots;
4. proposal-local pair escape;
5. 1px continuation;
6. independent sibling stencil;
7. proposal-local second pair escape;
8. second-pair continuation;
9. second-pair sibling stencil;
10. proposal-local third pair escape;
11. third-pair continuation;
12. third-pair sibling stencil;
13. proposal-local fourth pair escape;
14. fourth-pair continuation.

All geometry is generated with the unchanged public proposal objective. The **complete final continuation bank is frozen first**. Only then does Build64:

1. apply the existing Build41 held-out/full-pilot qualification;
2. freeze the complete qualified subset;
3. run deterministic single-candidate protected-data/list decoding;
4. accept only a frame that passes the existing HMAC.

Key, payload, ECC and HMAC do not create, refine, rank or prune geometry.

## New telemetry

When the fallback is reached, `v4-extract-phone` writes:

```text
build64-recovery: attempted=true seeds=... geometry-evals=... bank=... qualified=... decode-candidates=... list-frames=... max-confidence=... authenticated=...
```

This line is intentionally separate from Build43 and residual telemetry.

## Qualification gate

Run:

```sh
make v4-build64-phone-recovery-test
make v4-build64-phone-physical-test
```

The second command uses the qualified Go 1.26.0 toolchain and the complete retained nine-photo Build38 corpus.

Required matrix:

- controls front/mild/angle: reject, HMAC false, Build64 exercised and not authenticated;
- A/front: unchanged Build43 authentication; Build64 must not run;
- A/mild: unchanged existing-path authentication; Build64 must not run;
- A/angle: unchanged direct authentication; Build64 must not run;
- B/front: unchanged direct authentication; Build64 must not run;
- **B/mild: authenticate exact `v4-b38-phone-b` through Build64**;
- **B/angle: reject after Build64, HMAC false**.

Only a complete PASS of this matrix can justify promoting Build64 over the Build44 production baseline.

## Runtime

The deep fallback is intentionally expensive and bounded. It is paid only after the existing production path fails. The physical gate therefore uses a per-image timeout of up to 86400 seconds for fallback cases.
